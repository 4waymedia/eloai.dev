Developer Relations

EloAI is building something that requires explanation before it earns adoption. We need someone who can read a binary format spec, understand what it does, and write about it in a way that makes a developer want to build with it.

Full-time Remote Equity-included Early hire

The Communication Problem

EloAI has a thesis that is simultaneously obvious in hindsight and genuinely hard to explain before someone gets it: compression and meaning are the same operation. When you assign an ID to a word, you're not just making it shorter — you're placing it in a frequency-ranked semantic space. The compression address and the semantic coordinate are the same number.

The audiences who need to understand this are not the same. An ML researcher evaluating the Mixture of Libraries hypothesis needs the formal argument. A developer integrating the MCP server needs to know what sc_encode returns and why. A standards body considering browser-native dictionary pre-installation needs to understand the analogy to TLS certificate distribution. A general technical audience needs a version that doesn't require a tokenization background.

This role is not content marketing. It's the act of explaining a genuinely novel system to people who have every reason to be skeptical of it — and doing so without oversimplifying what makes it interesting.

What You'll Do

  • Own the developer documentation for the full EloAI system — the libelo C API, the MCP server interface, the .elo binary format spec, and the Python pipeline tools — written to the standard of documentation you'd actually want to read
  • Translate the MoL research thesis into accessible technical writing at multiple depth levels: a one-paragraph summary, a technical blog post, a deep-dive for NLP researchers, and a layperson explainer
  • Produce the IANA media type registration documentation for application/vnd.eloai.elo — a formal standards submission that requires both technical precision and process familiarity
  • Build the developer relations presence: GitHub README quality, issue response templates, community touchpoints, and the tone of every external communication from the project
  • Write the web standards proposal for browser-native dictionary pre-installation — a novel proposal that needs to be grounded in precedent (TLS certs, Unicode tables, font hinting) and argued on its merits
  • Maintain the internal spec library — SYSTEM1.md, ELO_FILE_FORMAT.md, and the growing set of component specs — so they stay accurate as the system evolves

Audiences You'll Write For

  • ML researchers: The MoL hypothesis, BPE critique, FAISS embedding initialization, fine-tuning experiment design — they will read carefully and push back hard on any imprecision
  • Systems developers: libelo API docs, binary format spec, LMDB storage layout, C/Python interface contracts — they need accurate, complete reference documentation
  • Web developers: MCP server integration, browser extension APIs, service worker approach — they want working examples and clear explanations of when to use what
  • Standards bodies: IANA registration, W3C proposal — formal, grounded in process, precise about scope and precedent
  • General technical audience: Blog posts, eloai.dev content, social presence — accessible without being reductive

What You Need to Understand

You don't need to have built a compression system. But you need to be able to read the spec and understand it well enough to write about it accurately. As a starting point:

# The things you'll be explaining
MoL        Mixture of Libraries — domain tokenization replacing BPE
.elo       binary format · magic "ELO1" · lossless · IANA-registered
libelo     C API · sc_encode / sc_decode · runs on Arduino
MCP        Model Context Protocol · IDE and agent integration
EPA        Evaluation–Potency–Activity · semantic space · Surov 2022
LMDB       14MB dictionary · 100ns lookups · fits in RAM
lossless   decode(encode(x)) == x · always · no exceptions

If reading that list makes you want to understand each line rather than glaze over it, this is the right role.

Who You Are

  • You write clearly about systems you've taken the time to understand. You don't paraphrase specs — you read them until you can explain them in your own words without losing precision.
  • You know the difference between being accurate and being complete. Good technical writing selects what a reader needs to know at this moment, not everything that's true.
  • You've worked with or alongside engineering teams closely enough to know when a spec has changed and a document hasn't caught up — and you treat that gap as your problem to fix.
  • You can write for different audiences without writing down to any of them. An ML researcher and a web developer need different explanations of the same system — not different levels of respect.
  • You're drawn to novel, technically complex ideas and find it satisfying to be the person who makes them legible to others.

What This Isn't

This isn't a role producing SEO content, social media posts, or marketing copy dressed up as technical writing. The work is documentation, explanation, and advocacy for a system that earns adoption by being genuinely well-described — not by being well-promoted.

Compensation is competitive for an early DevRel hire: base salary, meaningful equity, and co-ownership of how EloAI presents itself to the developer community from day one. The first impression of every external audience runs through this role.
