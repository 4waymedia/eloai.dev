Embedded Systems Engineer
C/C++ · On-Device Intelligence

EloAI's first hardware deployment is a robot that holds a conversation with no internet connection. We need an engineer who can make a 14MB dictionary run on constrained silicon — and knows why the constraints are the point.

Full-time Remote Equity-included Early hire

Why Embedded

Constrained hardware is not a limitation we're working around. It's the proof. If EloAI's cognitive architecture can hold a real conversation — perception, memory, emotion, reflection — on an Arduino with a 2GB storage drive and no network, then it has genuine boundaries. And a system with boundaries has identity.

The embedded deployment is the first full end-to-end test of the architecture: Whisper handles speech-to-text, the Arduino manages the interaction loop, the 14MB LMDB dictionary runs entirely in RAM, and every conversation is stored as .elo binary and reviewed afterward in the pipeline lab. No cloud. No inference API. Just the system, running.

The C++ requirement is architectural, not incidental. libelo — the public C API for EloAI — must run on anything. Arduino today. WASM tomorrow. Inference serving infrastructure eventually. You're designing the lowest layer of that stack.

What You'll Do

  • Design and implement libelo — the C/C++ public API exposing sc_encode, sc_decode, sc_open_library, sc_close_library — with stateless functions, explicit binary layout, and no dependencies that won't compile on bare metal
  • Port the LMDB dictionary lookup to a packed binary in-memory array (~7MB, ~5ns per lookup) that works within Arduino memory constraints
  • Integrate Whisper STT with the Arduino interaction loop — manage the pipeline from audio input through STT through EloAI encode/decode through response generation
  • Design the on-device memory database: every conversation stored as .elo on a 2GB drive, indexed for retrieval, reviewed via pipeline lab
  • Own the boundary between the Python pipeline tools and the C++ runtime — define the interface contract so both sides can develop independently
  • Write the embedded test harness: verify decode(encode(text)) == text on-device, measure encode/decode latency in microseconds, validate memory footprint against hard targets

Target Architecture

# Hardware target — v1
board      Arduino (interaction loop, memory, reflection)
stt        Whisper (speech → text)
storage    2GB drive · .elo corpus + memory database
network    none — fully isolated

# libelo public API
sc_open_library   (path) → handle
sc_encode         (handle, text, len) → stream
sc_decode         (handle, stream, len) → text
sc_close_library  (handle)

# Performance targets
lookup     ~5ns (packed binary array, in RAM)
dict_size  ~7MB in-memory (vs 14MB LMDB)
accuracy   decode(encode(x)) == x on all inputs

Who You Are

  • You've written C or C++ that shipped on hardware with real memory constraints — not a dev board with 512MB of RAM.
  • You think in terms of memory layout before you think in terms of data structures. You know the difference between what a struct looks like in code and what it looks like in memory.
  • You design public APIs carefully. libelo will be called from Python, potentially from Rust, eventually from browsers. Naming, ownership, and error handling decisions made now are hard to change later.
  • You've integrated audio pipelines or real-time sensor inputs at the hardware layer — not just called a cloud API.
  • You find the idea of a cognitive architecture running on a $40 microcontroller more interesting than the same architecture running on a GPU cluster.

What This Isn't

This isn't firmware for a consumer product. There's no hardware vendor, no production run, no compliance checklist. The first robot is a proof of concept — the goal is a working conversation, logged in .elo, reviewed in the pipeline lab, demonstrating that the architecture has a self to refer back to.

Compensation is competitive for an early systems hire: base salary, meaningful equity, and co-ownership of the architecture decisions that will define every future deployment target. The embedded build is where the thesis gets physically tested.
